# 门户增长复盘与长期实验机制

## 目标

把每次内容、SEO、产品或渠道发布记成可复盘动作，用同一套口径持续回答三个问题：流量从哪里来、用户是否完成核心行为、发布前后相对可比页面是否出现方向性变化。

原始分析事件只在云端任务运行期间读取。任务产物只有去标识的计数、比例、页面路径聚合和动作窗口比较，不输出访客或会话标识、IP 哈希、邮箱、搜索词、完整来源 URL、原始 UA。

## 固定运行机制

`.github/workflows/portal-growth-review.yml` 每周一北京时间凌晨运行，默认覆盖最近 14 个完整北京时间自然日。若某个动作的评估窗口与这 14 天相交，脚本会向前扩展到该动作的完整前窗；最大区间为 63 天。也可以手工同时指定起止日期。

工作流完成以下步骤：

1. 从 `PORTAL_SITE_URL` 推导站点 host，并读取公开 catalog，以便把静态研报落地页的 `report_id` 归入机构处理组。
2. 从 R2 的 `_analytics/events` 与 `_analytics_backup/events` 读取日期范围内事件。
3. 优先按 `event.id` 去重；旧事件没有 id 时，使用时间、类型、会话、访客、路径、报告和动作字段组成保守指纹。
4. 排除已识别机器人、后台事件和无法组成会话的匿名事件，按北京时间会话聚合。
5. 生成 JSON 与 Markdown 汇总，写入 Actions Step Summary，并保存为保留 1 天的登录可见 artifact。

## 固定指标

- 获客：自然搜索、AI 来源、普通外链、社交、邮件、明确活动、直接访问的会话数与占比。
- 核心行为：参与会话、报告打开、下载尝试、下载成功、报告申请、成功注册。注册只统计 `account_auth` 中 `action=register` 且状态成功的会话。
- 漏斗：各核心行为的会话数及其相对落地会话率。客户端事件可能丢失，因此它是会话行为发生率，不强行声称每一步严格按顺序发生。
- 留存：只以首次事件带有 `is_returning=false` 的访客为新访客；D1/D7 仅统计在区间末日前已经具备完整观察期的 cohort。
- 搜索意图：同一会话、规范化搜索词、一分钟时间桶只计一次，消除一次查询向多个数据源扇出的重复事件；报告不输出搜索词本身。
- 落地页：只展示至少 2 个会话的页面聚合，避免单个访问被产物间接识别。

### 站内搜索需求聚合

去重后的站内搜索意图只在任务进程内用受控词表分类，产物保留两组可重叠维度：与公开研报 hub 完全一致的 12 个已知机构，以及 `TOPIC_HUBS` 的 14 个已知主题。机构别名沿用建站脚本的中英文名称和代码规则；`MS`、`GS`、`DB` 等短代码必须是完整词，不能从其他单词中误命中。一个意图可以同时计入机构与主题，例如“高盛 AI”同时进入高盛和 `Tech / AI / Semis`；也可以同时命中多个主题，因此不能把各行相加当成总意图数。

每行只输出 `label`、去重意图数、搜索会话数，以及这些搜索会话中发生报告打开、下载成功、成功注册的会话数。默认少于 2 个意图的行不展示；未命中任何机构和主题的数量单独汇总，但不输出其搜索词。JSON、Markdown 和 Actions artifact 都不会写入原始 query、会话或访客标识、来源地址、UA 或数据源扇出字段。

运营时先按意图数识别真实需求，再比较搜索会话到报告打开、下载成功和注册的下游覆盖：高需求且下游弱的类别优先补齐搜索结果、专题页和可下载供给；高需求且下游强的类别适合扩充同机构／同主题内容与外部获客；未分类占比持续上升时，先在私有运行环境审查词表覆盖，再以新的受控标签迭代分类器，不能把原始搜索词带入周报。

## 发布动作台账

动作写入 `portal_suite/growth_actions.json`，至少包含：

- 唯一 id、动作名称、准确生效时间与可证伪假设；
- `pre_days`、`washout_days`、`post_days`；
- 处理组页面前缀和／或机构别名；
- 对照页类型与最低处理组样本量。

首个固化动作是“伯恩斯坦专题与公开研报索引”，生效时间为 2026-08-19 10:48:21（北京时间）：

- 前窗：2026-08-12 至 2026-08-18；
- 洗脱窗：2026-08-19 至 2026-08-21；
- 后窗：2026-08-22 至 2026-08-28；
- 处理组：从外部渠道首次落到伯恩斯坦专题页或 catalog 中伯恩斯坦研报详情页的会话；
- 对照组：同期从外部渠道首次落到其他公开研报详情页的会话。

洗脱窗不进入前后比较。输出同时给出处理组、对照组的相对变化，以及处理组在两组合计中的份额百分点变化。状态基于完整数据覆盖、最低样本量和份额方向生成，只写“方向性信号”，不把同期发布或渠道结构变化写成单一动作的因果证明。

## 每周决策规则

1. 先看 `data_quality`：日期不完整、机器人占比异常或处理组样本不足时，不下增长结论，优先补数据或延长观察。
2. 处理组份额上升，且报告打开、下载成功或注册没有明显变差：保留动作，并把同一结构扩展到下一个高需求机构或主题。
3. 外部落地增长但下游行为下降：保留可发现性，单独迭代标题承诺、首屏摘要、相关推荐与访问路径。
4. 处理组和对照组一起上升：记录为全站或渠道效应，不归功于单一专题动作。
5. 处理组份额下降：检查索引状态、canonical、页面可用性和搜索意图匹配；修正后登记为新动作，重新开窗口，不覆盖旧结论。
6. 每次发布前先写台账，再发布；每周复盘结论追加到任务记录或运营周报，保留原始动作 id，形成“假设—发布—观察—继续／迭代”的闭环。

## 已知边界

- 2026-08-19 同批发布还升级了 `page_view`、来源与会话字段，因此此前后的原始 PV、直接访问和 self-referrer 不能简单同比。动作复盘采用人类会话、外部首次落地和处理／对照比较降低口径变化影响。
- 站内事件无法还原外部搜索引擎的具体关键词或 AI 提示词；这部分只能结合各站长平台的查询数据补充。
- 当前没有购买或收入事件，报告不能推断收入归因。
- 结果是观察性证据。将动作复制到其他机构／主题时，应保留新的动作窗口，逐次验证可重复性。
