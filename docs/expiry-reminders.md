# 会员到期提醒运行说明

提醒只针对会员访问权限，不包含 API 授权、积分或 AI 研究次数。收件地址取发送前重新读取的账户邮箱。永久权限、停用账户、管理角色、系统生成邮箱和已退订账户均跳过；多个有效访问权限并存时采用最晚到期日，避免仍有权限却收到“已到期”。管理员关闭或过期记录对旧权益的覆盖关系沿用现有权限规则。

## 时间与频率

生产 cron 为 `* 2-3 * * *`（UTC），即北京时间每天 10:00–11:59 每分钟运行。标准提醒时间为到期日前 7 天、前 2 天、后 1 天的北京时间 10:00；每个到期周期最多 3 次，账户任意两次尝试至少间隔 48 小时。7 天以内或时长不明的短体验仅在到期前 1 天提醒一次。

扫描延迟时，前 7 天阶段可在前 2 天阶段之前补发；前 2 天阶段仅在实际到期前补发；到期后阶段最多保留至到期日后第 3 天 10:00。不会集中补发多个阶段。邮件写明实际到期时间和北京时间，并提供 info@kcdesk.com 与微信 MacroGate，不含付款链接。

续期改变最晚到期日后使用新周期；发送前再次核对账户身份、权限、到期日和退订偏好，旧周期任务取消。新周期仍遵守账户 48 小时间隔。

## 投递状态与重发

账户偏好、周期阶段和投递状态存于 R2 `_account/expiry-reminders-v1/accounts/`，通过条件写入更新。调用邮件服务前先保存 `pending`，并发扫描只允许一个任务取得阶段。

- `sent`：邮件服务已接受，不代表客户已收到或阅读。
- `failed`：邮件服务明确返回未接受。
- `unknown`：调用异常或结果不能确定。
- `pending`：发送前标记已保存，后续结果尚未可靠写回。
- `cancelled`：发送前重新核对发现续期、停用、退订或时间窗口变化。

以上状态都不会自动重试同一周期同一阶段，尤其不得清除 `pending` 或 `unknown` 来盲目重发。后续不同阶段仍遵守总次数与 48 小时间隔。邮件服务错误正文、异常详情、收件人和邮件内容不会写入扫描状态或日志。

## 预览、偏好与扫描状态

- 本人 `GET /api/account/expiry-reminders` 查看状态，`POST` JSON `{"enabled":false}` 关闭；`true` 可主动重新开启。
- 超级管理员 `GET /api/account-admin/expiry-reminders?email=...` 查看指定用户的到期状态及纯文本预览；该接口不发送邮件、不创建投递标记。
- 邮件中的签名退订链接 GET 仅显示确认页，确认 POST 才关闭提醒，避免邮件扫描器自动退订。

管理员响应 `scan` 包含 `date`、`complete`、`processed`、`attempted`、`errors`、`pending`、`updated_at`。`complete` 表示本次账号遍历结束，仍应检查 `errors`；`pending` 表示还保留未完成游标。没有投递成功或完整扫描证据时，不应报告全部客户已通知。

每轮最多处理 20 个账户、最多 9 次投递尝试。完成当日遍历后直接跳过余下 cron；未完成游标跨天保留，不每天回到第一页。最坏全为应发送账户时每轮最多前进 9 个；名义每日上限为 2,400 个无需投递账户或 1,080 次投递尝试，执行时长、并发租约及异常会降低容量。窗口结束仍 `complete:false` 时必须作为未完成处理，而不是声称覆盖全部账户。

Supabase 正常路径的外部请求上界为：1 次账号分页 + 20 次初次权益读取 + 9 次按账户 ID 复核身份 + 9 次再次权益读取 + 9 次邮件服务调用 = 48。身份复核采用单次 ID 查询，不走邮箱来源回退。条件写冲突重试仅访问 R2。独立 cron 分支不同时运行 Newsfeed 等外部任务；R2 请求属于独立内部服务调用，未计入此 48 次外部请求数。

## 启用与验证

`wrangler versions upload/deploy` 不会应用 Cron Triggers。应急发布工作流在 Worker 部署及现有线上 API 冒烟检查成功后，单独运行 `scripts/sync_portal_worker_schedules.py`；只有其 GET 读回核验成功才确认触发器配置已保存；这不证明实际 cron 已执行或客户已收到邮件。沿用现有 Cloudflare 账户/API token/Worker 名称，以及现有邮件服务配置（Brevo 或 Cloudflare Email binding），没有新增 secret。

同步只访问当前 Worker 的 `/schedules` API。先读取完整列表，保留未知计划；仅当四条已知 Newsfeed 时段全部存在时，将其合并为等价的 `*/10 0-3,5-6,17-18,23 * * *`，再加入 `* 2-3 * * *`。正常旧配置从 5 条变为 3 条，触发时间不变；如果保留未知项后仍超过 5 条，写入前失败。不修改路由或域名。

同步最多提交一次激活 PUT。回应不明时先 GET 核对，不盲目重发；读回要求最多 3 次内连续 2 次 cron 字符串集合完全一致。核验失败时，只有最新列表仍是本次已知旧值或目标值才恢复旧字符串列表并核验；遇到第三种并发状态或读不到当前状态时停止覆盖并报告 `conflict` 或 `unverified`。API 未提供已知的条件写保障，工作流发布锁及写前检查缩小并发窗口，不能宣称跨客户端原子更新。同步失败也触发现有 Worker 版本回滚。版本回滚本身不恢复触发器，因此应检查同步步骤的 `rollback` 结果；`verified` 才证明旧计划已恢复。

未配置可用邮件服务时扫描跳过。移除提醒 cron 可停止后续自动扫描；用户偏好和投递记录应保留。

`portal_suite/tests/expiry-reminders.test.mjs` 使用假 R2、假账户数据和假邮件服务，覆盖 500 以上账户的分页、并发去重、延期取消、退订、未知结果、时间窗口及真实 scheduled 入口的 48 次外部请求计数。测试不发送真实客户邮件，不读取线上账户记录或凭据。

定时触发器同步由 `scripts/test_sync_portal_worker_schedules.py` 离线验证，覆盖真实响应包裹结构、未知计划保留、等价时间集合、未知 PUT 回应、恢复和并发保护；不调用 Cloudflare 真实接口。
