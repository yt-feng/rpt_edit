# Newsfeed 访问、配额与私有申请架构

本文定义 Newsfeed 的服务端访问、会员配额、邮件订阅、超额申请、隐私记录与删除边界。浏览器展示必须服从服务端返回的策略；客户端常量、表单字段和本地存储都不是授权依据。

## 访问矩阵

| 身份 | 内置话题 | 自定义话题 | 邮件订阅 | 超额申请 |
| --- | --- | ---: | --- | --- |
| General 访客或免费账号 | 只读 | 0 | 不可用 | 不可用 |
| 有效会员，服务端核验的 qualifying membership period 少于 2 个月 | 只读 | 最多 3 个 | 可用 | 达到 3 个后可逐个申请 |
| 有效会员，服务端核验的 qualifying membership period 至少 2 个月 | 只读 | 最多 5 个 | 可用 | 达到 5 个后可逐个申请 |
| 服务端核验的 super 账号 | 只读 | 无上限 | 可用 | 不需要 |

只有 `kind=custom` 的话题计入配额；系统内置话题永远不占用 3/5 个名额。已有话题不会因为会员资格降级而自动删除，但降级后不得继续新增，直至自定义话题数量低于当前服务端限额。账号被停用时，所有受保护的 Newsfeed 写操作和邮件发送都必须拒绝。

有效会员与 qualifying months 必须来自服务端账号、权益和有效期记录。浏览器提交的 `role`、`tier`、`months`、`limit`、`count` 或类似字段不得参与授权。super 身份同样由服务端核验，不接受客户端声明。

## 设备标识与 IP 边界

General 访问使用浏览器生成并保存的随机 `visitor_id` 作为稳定的浏览器标识。需要设备级去重或服务决策时，Worker 使用服务端密钥对 `visitor_id` 做 HMAC，存储和比较的是派生值，而不是硬件序列号、广告 ID 或其他硬件指纹。

客户端 IP 只在服务端用于：

- 生成不可逆、截短或 HMAC 化的私有统计标识；
- 建立短期滥用与提交频率限制。

原始 IP 不进入公开分析事件，不作为跨设备硬件身份，也不返回浏览器。更换浏览器配置、清理本地站点数据或使用不同浏览器可能产生新的随机 `visitor_id`；这正是浏览器级标识而非硬件指纹的预期表现。

## 服务端配额契约

Newsfeed 首页、话题、探索和创建响应应返回同一份服务端权威策略，例如：

```json
{
  "policy": {
    "tier": "member",
    "custom_topic_limit": 3,
    "custom_topic_count": 2,
    "custom_topic_remaining": 1,
    "request_allowed": false
  }
}
```

`custom_topic_limit` 对 super 为 `null`，表示无上限。响应还包含兼容字段 `custom_topics: {count, limit, remaining}`；前端只负责展示服务端返回值，不自行推导 3、5 或无限。

创建自定义话题时，服务端必须在调用模型、抓取来源或写入完整话题对象之前原子占用一个名额。最后一个名额出现并发请求时，只能有一个请求成功；失败或超时的生成任务必须释放短租约。简单的“先列出对象、再比较数量、最后写入”不能作为配额保证。

达到限额时，创建接口返回稳定的冲突状态和机器可读代码，并附当前 `policy`。它不得调用模型，也不得写入新话题。前端保留用户输入，并提供一个明确、由用户主动点击的“申请增加该话题”操作；创建失败本身不能静默发送邮件。

## 邮件订阅

邮件订阅只对服务端核验的有效会员开放。订阅收件人固定为当前登录账号的有效邮箱；客户端提交的其他收件地址必须忽略或拒绝。每个账号的启用、停用、话题选择、语言、地区、发送时间和时区保存为私有设置。

定时发送和手动测试发送都必须在发送前重新核验账号未停用、会员仍有效、所选话题仍属于该账号。会员资格核验失败时应拒绝发送，不回退到客户端缓存的旧资格。

## 超额话题申请

达到 3/5 配额的有效会员可以对一个具体话题提交一次显式申请。申请接口只需要接收：

- 用户想增加的 topic；
- 输出语言与地区偏好；
- 当前站内页面路径；
- 反自动化 honeypot 字段。

申请人账号、邮箱、会员层级、qualifying months、当前数量和限额全部由服务端重新计算。请求中的 `to`、`recipient`、`requester_email`、`tier`、`months`、`count`、`limit` 等字段不得改变记录或邮件。

服务端发送目标固定为 `CONTACT_EMAIL`，其公开服务地址渲染为 <span>info&#64;kc&#100;esk&#46;com</span>。真实的私人转发邮箱只存在于邮件路由提供方的私有配置中，不进入浏览器、响应、源码、分析事件或日志。邮件正文中的 topic、用户名、页面路径和错误信息必须经过长度限制、控制字符清理和 HTML 转义。

只有在服务端重新确认账号已达到限额后才能接受申请；未达到限额时应引导用户正常创建。申请应具有同账号同规范化 topic 的去重、账号与 IP 频率限制，以及 `pending`、`sent`、`failed` 状态。记录必须先私有落盘再调用邮件提供方；发送失败时保留失败状态和可重试信息，不能丢失申请或谎报成功。

## 私有存档与管理员读取

每条超额申请的私有记录可包含：

- 不可猜测的 request ID 与规范化后的原始 topic；
- 账号 ID、账号邮箱和用户名；
- 会员层级、qualifying months、申请时的 custom count 与 limit；
- 语言、地区和清理后的站内页面路径；
- 创建、尝试、发送和更新时间；
- `pending`、`sent` 或 `failed` 状态、提供方消息 ID 与受限长度的最后错误。

授权管理员应能通过受保护的运维接口查询该私有存档，并看到加载、空列表、错误和刷新状态。当前契约不自动表示可视化管理后台已经发布；在前端管理区上线前，应描述为“运维私有存档”，不能向用户声称已有可操作的管理 UI。普通账号和非授权运营角色不得读取这些记录。

## 分析数据最小化

原始自定义 topic 可由配置的模型与搜索提供方在创建和刷新该话题所需的范围内处理；原始超额申请 topic 还会进入私有申请存档和对应通知邮件。它们都不进入 public analytics 或公共静态产物，持久化副本只保存在账号私有话题对象、私有申请存档和必要的通知记录中。

分析事件只记录改善漏斗所需的有界字段，例如页面、动作、成功或失败状态、会员 tier、custom count、limit、结果数量，以及不包含 topic 明文的 request ID 或单向摘要。分析接口继续执行同源校验、字段白名单、长度限制与私有管理员读取控制。

## 保留与删除边界

Newsfeed 数据分为四类：

1. 内置话题：产品内容，不属于单个账号数据。
2. 自定义话题、置顶和订阅设置：按账号私有保存，直至用户删除、替换、停用订阅、删除账号，或服务不再需要。
3. 派生新闻缓存：是可重建的运行数据，可按缓存策略过期或重建。
4. 超额申请：仅在处理申请、去重、防滥用、支持和法定义务所需期间保留；适用时可响应访问、更正或删除请求。

所有 Newsfeed 删除都必须限定在明确的 Newsfeed 对象或命名空间内，并先核验目标。本文不授权 Newsfeed 任务删除或缩短以下资产的保留期：

- 已保存的报告 PDF 与报告正文；
- 已解析的 Charts、Chart 图片、Chart 索引与来源关联；
- 报告研究索引、Course 材料或其他会员资产；
- GitHub 缓存或其他运维对象。

同样，PDF 容量清理、Charts 清理、静态发布清理或 GitHub 缓存清理不得通过宽泛前缀处理 Newsfeed 的话题、设置、配额记录或申请存档。新增任何 Newsfeed 清理必须使用独立开关、显式前缀、非破坏性预览和定向测试；它不能复用 PDF 或 Charts 的删除范围。

## 失败与发布顺序

- 账号或会员资格暂时无法核验时，写操作、邮件订阅和超额申请应关闭，不按更高权限放行。
- 配额冲突应在模型调用前返回；存储写入失败不得消耗永久名额。
- 邮件提供方失败时，私有记录保留为 `failed`，响应明确为可重试，不返回提供方密钥、内部对象路径或私人转发邮箱。
- 先发布服务端策略、原子配额和申请接口，再发布依赖机器可读错误码的新前端。旧前端可以显示通用限额错误，但不能绕过服务端限制。
- 生产 smoke 只验证匿名申请被拒绝、非管理员无法读取私有存档等无副作用路径；不得为了 smoke 发送真实申请邮件。
